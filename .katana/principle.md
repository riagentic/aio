# Major aio principles

## These are not really measurable criteria, but rather rules that must be followed

- aio framework is intuitive
- aio (surface) is compact
- aio doesn't break surface compatibility (i.e. old applications keep running with a new version)
- quality requests leading to breaking surface compatibility are saved in untracked/v2.md
- aio framework logs all real errors and warnings
- aio framework doesn't log artificial, false or unreal errors and warnings
- aio framework is helpful to the developer, i.e. it provides correct information, context and hints about issues and how to use aio correctly
- aio framework is not confusing (principles are clear)
- aio never makes the developer's life harder than necessary
- aio uses a balanced approach, "doable quality", i.e. as high quality as possible that is still reasonably doable
- aio chooses the right, sound and robust architecture (as simple as possible while effective, avoiding overengineering)
- aio provides a surface for users to build and maintain applications easily while doing the hard stuff itself internally
- aio has a perfect onboarding experience (i.e. smooth, intuitive, flawless)
- aio has optimal facilities for humans and for AI agents
- aio uses a few clean concepts that it promotes across the entire framework
- aio doesn't use incompatible approaches where it can use clean, compatible and reusable ones
- aio tries to minimize its learning curve
- aio provides reusable functionality that can be used by many different applications
- aio refuses feature requests that can be used only by one specific app and by no one else; such a feature belongs to the app, not to the framework
